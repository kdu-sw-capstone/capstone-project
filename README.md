## 브랜치 전략

| 브랜치 | 용도 |
|--------|------|
| `main` | 배포 및 발표 가능한 안정 버전 |
| `develop` | 기능 통합 및 테스트 브랜치 |
| `feature/*` | 새로운 기능 개발 |
| `bugfix/*` | 일반 버그 수정 |
| `hotfix/*` | 배포 또는 발표 버전의 긴급 수정 |
| `refactor/*` | 기능 변경 없는 코드 구조 개선 |
| `docs/*` | 문서 작성 및 수정 |
| `chore/*` | 환경 설정 및 저장소 관리 |

일반 작업의 개발 흐름은 다음과 같습니다.

```text
feature/*
bugfix/*
refactor/*
docs/*
chore/*
    │
    ▼
develop
    │
    ▼
main
```

`main`과 `develop` 브랜치에는 직접 Push하지 않으며 Pull Request를 통해 병합합니다.

긴급 수정은 최신 `main` 브랜치에서 `hotfix/*` 브랜치를 생성합니다. 수정 완료 후 `main`에 병합하고, 동일한 변경 사항을 `develop`에도 반영합니다.

```text
hotfix/* → main → develop
```

## 협업 절차

1. 최신 `develop` 브랜치를 Pull합니다.
2. 작업 목적에 맞는 브랜치를 생성합니다.
3. 기능 개발 또는 문서 작업을 진행합니다.
4. Commit 후 Push합니다.
5. Pull Request를 생성합니다.
6. 코드 리뷰를 진행합니다.
7. 승인 후 Merge합니다.

민감한 정보(API Key, 비밀번호, 개인정보 등)는 저장소에 Commit하지 않습니다.

자세한 협업 규칙은 [CONTRIBUTING.md](CONTRIBUTING.md)를 참고합니다.
