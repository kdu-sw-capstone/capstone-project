# FOCURVE

**집중 환경을 설정하고, 브라우저의 방해 요소를 줄이며, 기록을 바탕으로 다음 집중을 개선하는 서비스**

경동대학교 소프트웨어학과 캡스톤 디자인 팀 프로젝트입니다. 이 저장소에서 Web·Server·Chrome 확장프로그램의 소스 코드, 설계 명세와 협업 기록을 함께 관리합니다.

현재는 **필수·추가 MVP의 구현 전 설계를 정리하고 개발을 준비하는 단계**입니다. 기능별 구현과 검증 결과는 작업카드와 통합 현황에서 관리합니다.

[설계 통합본](docs/design/FOCURVE_설계_통합본.md) · [설계도 목록](docs/design/07_설계도/페이지목록.md) · [개발 현황](docs/implementation/통합현황.md) · [협업 규칙](CONTRIBUTING.md)

## 주요 기능

| 단계 | 기능 |
|---|---|
| 필수 MVP | 회원가입·로그인, 비회원 사용, 계정 연결과 자료 가져오기 |
| 필수 MVP | 사이트 관리, 사이트·Shorts 제한, 집중 시작·종료와 실제 적용 상태 확인 |
| 필수 MVP | 행동 기록, 반복 접근·집중 통계, 대시보드와 화면 설정 |
| 추가 MVP | 사이트 내부 기능 제한, 키워드 제한, 성인 사이트 제한, 민감 이미지 블러 |
| 추가 MVP | 집중 예약, 일시정지·재개, 세션 메모 |
| 추가 MVP | 이용 시간·행동 지표·시간대 분석, AI 피드백 |

Chrome 확장프로그램은 필수 MVP부터 함께 구현합니다. 회원·비회원별 지원 범위와 저장 방식은 [기능 범위 명세](docs/design/01_UX_기능설계/01_기능범위.md)를 따릅니다. PC 앱 확장은 필수·추가 MVP의 구현과 검증을 마친 뒤 진행하는 후속 개발 단계입니다. 현재 상세 명세는 Web·Server·Chrome 확장프로그램을 다룹니다. 모바일 확장은 미정입니다.

## 시스템 구성과 기술

| 영역 | 설계 기준 기술 | 역할 |
|---|---|---|
| Web | React | 설정·세션 요청·대시보드·기록·통계 화면 |
| Server | Spring Boot | 인증·권한·API·데이터 저장·집계 |
| Database | MySQL | 계정과 서비스 데이터 관리 |
| Extension | Chrome Manifest V3 | 실제 브라우저 제어·정책 적용과 해제·이벤트 수집·비회원 로컬 실행 |

Web에서 설정하거나 요청한 정책은 Extension의 실제 적용·해제 결과를 확인해 상태에 반영합니다. 세부 처리 순서는 [API·연동 명세](docs/design/02_시스템_테크설계/04_API_연동.md), 데이터 구조와 복구 기준은 [데이터 명세](docs/design/02_시스템_테크설계/05_데이터_복구.md)를 따릅니다.

PC 확장 방향과 현재 상세 설계의 경계는 [개발 단계와 PC 후속 확장 계획](docs/design/02_시스템_테크설계/09_PC_후속확장계획.md)을 따릅니다.

진행 순서는 **개발 환경 구성 → 필수 MVP → 추가 MVP 완료·검증 → PC 앱 확장**입니다. 각 단계에서 테스트·안정화를 병행하며 PC 세부 일정은 별도 수립합니다. 첫 연동은 사이트 설정부터 집중 시작·차단 확인·종료·해제까지 작은 단위로 연결합니다. 기능별 검증과 실제 연동 확인은 개발 중에도 진행합니다.

실제 진행 상태는 [통합 현황](docs/implementation/통합현황.md)과 각 작업카드에 기록합니다. 설계 문서 작성이나 코드 생성만으로 기능 완료를 표시하지 않습니다.

## 브랜치와 협업

| 브랜치 | 용도 |
|---|---|
| `main` | 통합 검증을 통과한 안정 버전 |
| `develop` | 기능 통합과 연동 확인 |
| `feature/*` | 기능 개발 |
| `fix/*` | 오류 수정 |
| `docs/*` | 문서 작성·수정 |
| `refactor/*` | 기능 변경 없는 구조 개선 |
| `chore/*` | 개발 환경·저장소 관리 |

기존 `bugfix/*` 작업은 이름을 바꾸지 않고 마무리할 수 있습니다.

1. 최신 `develop`에서 작업 브랜치를 만들고 기능·담당을 작업카드에 기록합니다.
2. 관련 설계를 확인한 뒤 구현하고 검증 결과를 남깁니다.
3. 커밋·Push 후 `develop`을 대상으로 Pull Request를 만듭니다.
4. 다른 구성원의 검토를 거쳐 병합하고 실제 연동을 확인합니다.
5. 통합 검증을 통과한 안정 버전을 PR로 `main`에 반영합니다.

`main`과 `develop`에는 직접 Push하지 않습니다. API Key·비밀번호·토큰·실제 개인정보와 `.env`는 커밋하지 않습니다.
