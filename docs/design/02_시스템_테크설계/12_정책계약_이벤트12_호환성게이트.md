# 정책 계약 확정 — 2026-10-09 사용자 명시 요청

이 문서는 사용자 최신 확정 정책을 반영한다. 기존3인 배정 유지. Server 구현/자동 검증과 제품 Core·Content·실제Chrome 통합은 별도 상태다. 기존1.1 저장 JSON/이벤트를 마이그레이션하거나 다시 쓰지 않는다.

## 이벤트 schema_version 1.2

기존 envelope/event_type/API `/api/v1/events/batch`, `/status`, E bearer·소유권·세션·snapshot·확인된RUN 검증은 유지한다. 새로운 접근 payload만 다음 의미를 사용한다.

- target_kind SITE/FEATURE, target_host 및 **target_key는 실제 방문한 정규화 호스트**(접두사 없음). URL의 hostname만 추출, 소문자 IDNA/끝점 정규화, 경로/query/port 제외. www 및 각 하위 호스트는 별도 대상이다. 등록 URL 제약은 별개이며 임의로 상위 호스트로 축약하지 않는다.
- matched_policy_host는 frozen snapshot에서 선택한 가장 구체적인 canonical_host. 선택 행이 없으면 명시적 null. 상위 정책이면 상위 호스트, 실제 방문 호스트를 대신하는 키가 아니다.
- blocked_reasons는 이미 확인된 차단 이유의 중복 없는 배열. 기존 reason 코드 USER_SITE/ADULT_DOMAIN/KEYWORD/FEATURE 유지. RECORDED_ACCESS에는 reason=RECORD, blocked_reasons=[].
- 단일 reason은 기존 조회/DB 호환을 위한 대표 사유. USER_SITE→ADULT_DOMAIN→KEYWORD→FEATURE 순서로 배열에서 선택하며 다른 확인된 사유를 버리지 않는다. 여러 평가가 같은 navigation/실제host를 차단해도 접근1건이다. 확정된 차단을 추가 탐지 때문에 기다리지 않는다. 새로운 원문 텍스트/전체 URL을 저장하지 않는다.
- 같은 session/실제host의 순서는 기존 access_seq로 정한다. target_access_index는 기존1-based 유지, **repeat_count=index-1**(0/1/2…). is_repeat는 repeat_count>0, summary.repeat_access는 해당 접근 건수이며 repeat_count를 합산하지 않는다. 내부 기능은 feature_code/rule_id로 별도 식별하며 호스트 집계키에 경로/feature를 넣지 않는다.
- 동일 event_id와 동일 envelope는 DUPLICATE. 동일ID의 다른 내용은409 EVENT_CONFLICT. 늦게 알게 된 이유를 기존ID에 덧붙여 재전송하지 않는다. 이후 사유 보강이 필요하면 별도 annotation 계약이 먼저 필요하며 현재는 제공하지 않는다.

기존 schema1.1은 SITE:<host>/FEATURE:<host>:<feature> 의미와 집계를 보존한다. 1.1로 barehost/new metadata를 보내지 않는다. 이중 수용 경로이며 신규 Core/Content는1.2 payload로 전환해야 한다. PR17의 SITE:<등록상위host>는 기존 Server 계약과도 불일치하므로 계속 거절한다. Server가 방문 호스트를 추측해 잘못된 legacy payload를 고쳐 저장하지 않는다.

## DB 및 조회 호환

기존 access_events.reason은 대표 사유, matched_policy_host/blocked_reasons는 event_receipts.payload JSON에서 원본과 함께 영속 보존한다. 새 테이블/컬럼/기존 migration 수정이 필요하지 않다. RecordQueries는 신규1.2에 실제host partition, 기존1.1에 기존target partition을 사용한다. 기록 목록·상세는 repeat_count, matched_policy_host, blocked_reasons를 추가 반환하고 기존필드는 유지한다. 과거 최소receipt에 없는 정책 메타데이터는 null로 반환하며 임의 추정하지 않는다.

## Snapshot1.2 활성화와 전체 검증

신규1.2의 필드명/형식은 기존 Snapshot 계약 그대로다. 새로운 Snapshot 필드를 만들지 않았다. SnapshotValidation은 버전/strategy·기본 식별/시각/owner/source_version·sites·정책/자료형·ContentPolicy 구조를 신규 발급 transaction 안에서 검증한다. 부분 정책을 저장해 정상 시작으로 처리하지 않는다. 이 Server 검사만으로 실제 Extension 적용을 확인한 것이 아니다.

- 신규 발급 기본 OFF: 프로세스 환경 SNAPSHOT_1_2_ENABLED=false.
- 실제 Server↔제품Extension1.2 호환 검증 후 SNAPSHOT_1_2_ENABLED=true와 SNAPSHOT_1_2_VERIFIED_EXECUTORS=<검증한 executor UUID들을 쉼표로 구분> 설정. DB나 저장소에 secret을 추가하지 않는다. 활성화 전에 실제Chrome적용·보고/복구 증거를 기록한다.
- 미활성 또는 비검증 설치는503 SNAPSHOT_COMPATIBILITY_REQUIRED. 1.1로 조용히 fallback해서 상하위 정책 의미를 바꾸지 않는다. 새 snapshot/session/command/lock을 만들지 않는다. 이미 처리된 멱등 요청은 원래 응답을 반환한다.
- test profile에 한해 verified-executors=*로 합성 설치를 허용한다. 일반 실행에서는 *를 인증된 설치 목록으로 인정하지 않는다. 이는 지원 버전 협상 프로토콜이 아니라 임시 운영 안전장치다. 실제 capability handshake 계약/제품 연결은 Core·Server 후속 대상이다.
- 기존1.1/1.2 snapshot의 조회·보고·해제·기록은 신규발급 gate의 대상이 아니다. 저장원문 유지. Core는 미지원/잘못된 전체정책을 적용 전에 거절하고 journal→규칙설치→실제관찰→보고 순서를 지켜야 한다. 기존유효세션을 malformed 새 명령 때문에 임의 해제하지 않는다. 이 부분은 실제Core검증 필요.

## 사이트·전역 정책

가장 구체적인 사이트 행 전체를 선택한다. parentBLOCK+childBLOCK은 각각 차단, parentBLOCK+childALLOW는 child 사이트상 허용이나 전역제한 예외가 아니다. adult_domains와 keywords는 각각enabled 및 자기 exceptions만 평가한다. 성인 예외는 키워드를 해제하지 않고 그 반대도 같다. USER_SITE BLOCK은 전역예외와 무관하다. 유효차단 하나라도 있으면1건 차단, 이미 확인된 이유들을 함께 기록한다.

Server는 신고된 복수사유가 당시 사이트정책/전역enabled·예외와 양립하는지 검사한다. Content실제 탐지를 대신 수행하거나 그 성공을 주장하지 않는다. 현재 신규snapshot의 ContentPolicy는 default disabled이며 전역설정 저장/Content실행 경로 연결은 추가MVP·담당 후속 구현 대상이다. 모의policy 활성화 테스트를 제품 전역설정/차단 완료로 표시하지 않는다.
