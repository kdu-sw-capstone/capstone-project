# FOCURVE 설계·기술 검토

기준: 2026-10-03, `develop`의 `f7341cc0d24600e1cd4ac939b468aac08f1887e7`와 팀장 확인 사항.

## 판정과 검토 범위

React Web + Spring Boot Server + MySQL + Manifest V3 Extension의 책임 분리는 유지할 수 있다. 그러나 **현재 설계 그대로 전체 구현을 시작할 준비가 끝났다고 판정할 수는 없다.** 기본 기능에는 명세 충돌이 있고 추가 기능에는 구현 계약이 남아 있다. 실행 코드는 아직 없다는 점을 팀장이 확인했다. 아래 평가는 문서·공식 API에 근거한 설계 검토이며 실제 기능·성능·배포 검증 결과가 아니다.

Markdown, API·이벤트·ERD 텍스트, XLSX 6개, draw.io 29개 페이지의 구조, 예시 JSON을 점검했다. Figma는 Low-Fi와 기본/전체 High-Fi 일부 페이지의 프레임 메타데이터를 대조했다. 모든 화면을 시각적으로 검수하거나 모든 상태 전이를 실제 실행한 것은 아니다. PDF 등 과거 발표 자료는 현재 실행 계약으로 간주하지 않는다.

확정된 일정은 [개발 계획](FOCURVE_개발계획_v1.3.md), 개인별 책임은 [팀 가이드](../../TEAM_GUIDE.md)를 따른다. 10월 8일 기본 MVP, 15일 추가 MVP는 빠른 목표, 최대 구현 목표는 10월 말이다. 23일까지 UI 확정 후 교체하고 그 UI로 Desktop을 구현하며 MVP 이후 통합 테스트·문서화와 병행한다. Desktop 완료일은 미정이다.

| R06 · 중간 | 기본 범위에는 소셜 로그인이 있지만 지원 제공자·연결 정책이 정해지지 않았고 API는 이메일 흐름 중심이다. | 제공자, 기존 이메일 계정 충돌, 계정 연결/해제, Extension 인증 방식 결정 및 오류 계약 추가. | 팀 결정 대기 |

R01과 R02는 아직 승인된 제품 정책이 아니다. 팀장에게 이점과 구현 비용을 설명했으며, 확정 전 API·XLSX·Figma의 기존 동작을 임의로 덮어쓰지 않았다. 이번 변경만으로 모든 설계 문서의 정합성 문제가 해소되었다고 표시하지 않는다.

## 기술별 사용 가능 조건

| 영역 | 설계 판정 | 구현 조건·실증 항목 |
|---|---|---|
| React / Spring Boot / MySQL / REST | 기본 구조 유지 가능 | 배포 주소·버전·인증·권한·오류 규격 확정. MySQL 동시 시작 제어는 트랜잭션으로 검증 |
| MV3 사이트 차단 | 가능, 실제 검증 필요 | `declarativeNetRequest`의 main_frame 규칙·예외·서브도메인·리다이렉트·해제 복구 검증 |
| 차단 접근 기록 | 수집 방식 검증 필요 | 디버그 콜백에 의존하지 않고 사용자 접근 1회와 실제 차단 결과를 연결. 탭/이동/재시도 중복 제거 |
| Shorts / Reels / 추천·댓글·자동재생 | 서비스별 PoC 필요 | 직접 URL·SPA 내부 이동·뒤로 가기·새로고침·DOM 변경·재진입·정책 해제. Shorts 내부 연속 스크롤은 반복 진입과 구분 |
| 세션 타이머 / 예약 | 종료 시각 기반 복구 필요 | 메모리 타이머가 유일한 기준이면 안 됨. 절전·종료·재시작 후 시각과 적용 정책 재조정. 초 단위 정시 실행 보장은 하지 않음 |
| 비회원 / 오프라인 / 재전송 | 가능, 영속 상태 필요 | 로컬 용량 부족·쓰기 실패, 서비스 워커 종료, 계정 전환, event_id 중복 제거·확인 응답 유실 검증 |
| 사이트 이용 시간 | 별도 측정 계약 필요 | 여러 탭, 활성 창, 유휴·절전, 종료 누락의 시간 계산 정의. 접근 이벤트 횟수만으로 이용 시간을 계산하지 않음 |
| 성인 사이트 / 이미지 블러 | 현재 명세로 품질 보장 불가 | 분류 데이터·모델·실행 위치·지원 대상·오탐·성능 기준 결정 후 PoC. 전 사이트 완벽 제한으로 표현하지 않음 |
| AI 피드백 | 제공자·처리 계약 필요 | 입력 최소화·사용자 안내·실패·기록 부족·비용 및 시간 한도. 사용자 확인 없이 정책 변경하지 않음 |
| PC Desktop | UI 재사용 가능성 있음, 실행 계층은 별도 | Desktop 기술·지원 OS·제어 범위 결정. Chrome 제어와 OS 프로세스 제어를 구분하고 플랫폼 연동 계층 설계 |

Chrome MV3 서비스 워커는 유휴 상태에서 종료될 수 있다. 5초 간격 메모리 폴링을 상시 보장하는 구조는 부적절하다. 서버 명령은 저장하고, 확장이 깨어날 때 상태 조회·복구할 수 있어야 한다. 지속 연결을 택하더라도 재연결·명령 중복·응답 유실 계약이 필요하다. [Chrome 서비스 워커 수명](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)

alarms는 최소 간격과 지연 제약이 있고 절전 중 기기를 깨우지 않는다. DNR dynamic 규칙은 재시작 후 남지만 session 규칙은 브라우저 종료·업데이트 때 제거된다. 어느 방식을 써도 적용 스냅샷·종료 시각·복구 절차를 함께 검증해야 한다. [alarms](https://developer.chrome.com/docs/extensions/reference/api/alarms), [DNR](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)

`onRuleMatchedDebug`는 unpacked 확장의 디버깅용이다. 이를 배포판의 접근 기록 수집 수단으로 사용하면 안 된다. navigation 이벤트와 차단 페이지 등을 사용하는 후보는 실제 차단 시 필요한 정보가 남는지 PoC로 확인해야 한다. [DNR 디버깅](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest), [webNavigation](https://developer.chrome.com/docs/extensions/reference/api/webNavigation)

Content Script는 페이지 DOM 제어에 적합하다. 서버 통신·인증 정보·재전송 큐는 공통 background 경로로 모으는 방식을 권장한다. Content Script에서의 cross-origin 요청은 페이지 출처 제약을 받는다. 메시지 수신자는 허용한 작업·대상만 처리해야 한다. 이는 채지민의 이벤트 생성·전송 책임을 바꾸는 것이 아니라 내부 전달 경로의 제안이다. [Content Script](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts), [네트워크 요청](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests)

## 유지할 설계

- 세션 시작 시 정책 스냅샷을 만들고 실행 중 설정 변경은 다음 세션에 적용한다.
- HTTP 요청 수락과 실제 정책 적용·해제 성공을 구분한다.
- 미전송 이벤트는 영속 큐에 두고 event_id 기준으로 중복 저장을 막는다.
- 비회원 자료는 로그인만으로 자동 업로드하지 않고 선택·저장 확인을 거친다.
- 소유권은 클라이언트가 보낸 user_id를 신뢰하지 않고 인증 정보로 검증한다.
- 반복 접근은 같은 세션·같은 대상의 두 번째 접근부터 계산한다. 회원과 비회원의 결과가 같아야 한다.

## GitHub 정리

- 현재 폴더는 `frontend/`, `backend/`, `extension/`, `docs/`다. 대문자 Backend/Frontend나 Core/Content 하위 폴더는 현재 구조가 아니다.
- `main`·`develop`은 승인 1개를 요구하는 PR 보호가 있다. CI 워크플로와 필수 상태 검사는 아직 없다.
- 열린 기능 작업 이슈가 부족하다. 환경·인증·Core 차단·Content Shorts·이벤트·통계·통합 검증 단위로 이슈를 만들고 담당·명세·기대 결과를 연결한다.
- `main`과 `develop`의 커밋 이력은 분기되어 있다. 앞섬/뒤처짐 숫자만으로 누락이라고 판단하거나 강제 Push하지 않는다. 배포 PR에서 실제 파일 차이와 병합 결과를 확인한다.
