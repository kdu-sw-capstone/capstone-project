# 호스트별 정책 우선순위 — 2026-10-08 사용자 요청 반영

상태: 사용자 명시 지시로 등록/선택 규칙 변경 확정. Web·Server·DB 구현과 독립 검증 대상이며 실제 Extension 적용 완료가 아니다. 기존3인 담당 유지.

## 이전 규칙과 변경 이유

기존 API 명세 ‘동일하거나 포함관계인 등록 범위는409’, SITE-02 ‘중복 범위’, sites ERD ‘중첩범위 검사’ 때문에 naver.com의 하위 도메인 포함 설정이 chzzk.naver.com 별도 등록을 막았다. 이를 다음 규칙으로 대체한다. 최신 사용자 지시가 이전 본문·상세 도면보다 우선한다.

## 등록·정규화·선택

1. http/https URL 또는 host에서 호스트만 추출한다. 소문자 IDNA(ASCII), 마지막 점 제거를 적용한다. www·chzzk 같은 레이블을 삭제하거나 등록 가능 상위 도메인으로 축약하지 않는다. 경로·query·fragment는 관리 범위가 아니다. 기존 자격정보 URL/IP/localhost/명시적 port 거절은 유지한다.
2. 같은 계정의 정규화된 canonical_host가 **정확히 같은 경우만** 중복이다. include_subdomains·분류·정책이 달라도 같은 호스트를 별도 등록하지 못한다. 다른 계정에는 같은 호스트 등록 가능.
3. 상위/하위/형제 호스트는 각각 등록·수정·분류·정책 설정할 수 있다. include_subdomains는 등록 가능 여부가 아닌 해당 행의 적용 범위다.
4. 접속 호스트 h는 `h == canonical_host` 또는 `include_subdomains && h.endsWith('.' + canonical_host)`일 때 매칭한다. `notnaver.com`, `naver.com.evil.example`은 naver.com에 매칭하지 않는다.
5. 매칭된 행 중 **레이블이 가장 많은 호스트**를 하나 선택한다. 매칭 후보는 조상/자손 사슬이므로 가장 긴 canonical_host와 같다. 선택 후 그 행의 purpose/access_policy/feature_policies 전체를 사용한다. 등록 순서·정책 강도·단순 첫 DB 행으로 선택하지 않는다. 부모의 BLOCK/Shorts 설정을 자식의 ALLOW/해제 설정과 합치지 않는다.
6. 사이트 행을 선택한 뒤, 그 정책의 BLOCK→기존 전역 성인/키워드 제한→해당 행의 내부 기능 제한→RECORD/ALLOW 순서를 유지한다. 자식 ALLOW가 전역 성인/키워드 예외까지 새로 만드는 것은 아니다. 한 navigation/target의 최우선 이유1건 규칙 유지.
7. 수정·삭제·재등록은 다음 세션부터 적용한다. 활성/종료 세션의 기존 snapshot JSON, 식별자, 기록은 재계산·덮어쓰기하지 않는다.

## API·DB 계약

- API-SITE-03 POST, API-SITE-04 PATCH의 경로와 요청/응답 형식·CSRF·소유권·Idempotency-Key·If-Match 유지. 기존 오류 코드409 `SITE_SCOPE_CONFLICT`는 유지하되 의미를 **정확한 호스트 식별자 충돌**로 좁힌다. Web은 ‘같은 호스트가 이미 있음’으로 표시한다.
- DB의 `UNIQUE(user_id,canonical_host)`와 사용자 행 잠금 유지. 포함 범위 검사만 제거. 기존 migration V1~V6 변경/DB 재초기화/데이터 이동 없음.
- 삭제된 행은 기존 호스트 식별자를 보존한다. 같은 호스트의 새 등록은 기존 행을 복원한다. 다른 행을 삭제된 호스트로 변경하는 PATCH는 동일 DB 식별자 충돌409다. 기존 보관/복구 동작 유지.

## 새 세션 Snapshot1.2

새로 만드는 정책 snapshot만 `format_version: "1.2"`, `site_match_strategy: "MOST_SPECIFIC_HOST"`를 갖는다. `sites`의 구조는 기존 Site와 같다. sites는 호스트 레이블 수 내림차순, 동률은 canonical_host ASCII 오름차순으로 직렬화한다. 각 접속 호스트에 매칭되는 가장 구체적인 행을 선택해야 하며 모든 행의 차단을 합집합으로 만들면 안 된다. 새 전략을 이해하지 못하는 실행기는 임의 적용하거나 APPLIED를 보내지 말아야 한다.

```json
{
  "format_version": "1.2",
  "site_match_strategy": "MOST_SPECIFIC_HOST",
  "sites": [
    {"canonical_host":"chzzk.naver.com","include_subdomains":true,"purpose":"DISTRACTION","access_policy":"BLOCK","feature_policies":[]},
    {"canonical_host":"naver.com","include_subdomains":true,"purpose":"GENERAL","access_policy":"ALLOW","feature_policies":[]}
  ]
}
```

위 JSON은 변경 필드 중심 발췌이며 site_id·version·snapshot 식별자 등 기존 필수 필드를 생략한 설명용이다. 실제 API에는 기존 필드를 유지한다. 이벤트 schema_version1.1은 변경하지 않는다. 기존 format_version1.1 snapshot은 원문 그대로 읽고 복구/기록에 사용하며1.2로 재작성하지 않는다. 세션 시작 시 사용자 잠금 아래 현재 설정을 고정하므로 동시 수정이 중간에 섞이지 않는다.

## 공용 검증 예

| 등록 설정 | 접속 호스트 | 선택 결과 |
|---|---|---|
| naver.com 포함/일반/ALLOW + chzzk.naver.com 포함/방해/BLOCK | chzzk.naver.com, live.chzzk.naver.com | chzzk.naver.com BLOCK |
| 위와 같음 | naver.com, www.naver.com | naver.com ALLOW |
| 위와 같음 | notnaver.com, naver.com.evil.example | 매칭 없음 |
| 위 + clips.chzzk.naver.com 미포함/일반/ALLOW | clips.chzzk.naver.com | 더 구체적인 ALLOW |
| 위와 같음 | x.clips.chzzk.naver.com | clips는 미포함이므로 chzzk의 BLOCK |
| naver.com 포함/BLOCK + chzzk.naver.com 미포함/ALLOW | chzzk.naver.com | 자식 ALLOW, 부모 BLOCK 합치지 않음 |
| 위와 같음 | live.chzzk.naver.com | 부모 naver.com BLOCK |

## Extension 전달 사항과 미검증

윤종민(Core): 회원/비회원 동일 정규화·중복/선택 규칙, snapshot1.2 해석, MV3 네트워크 규칙의 도메인 경계·자식 허용 우선순위·등록 순서 독립성을 실제 Chrome에서 검증한다. 단순 부모 차단규칙+자식 규칙 추가만으로 충돌 해결을 가정하지 않는다.

채지민(Content Control): Core가 선택한 동일 site_id/host 행의 Shorts 등 내부 기능 정책만 적용하고 부모 설정을 섞지 않는다. 실제 적용/해제 결과·이벤트 대상은 접속한 canonical host로 보고한다.

김다훈(Web·Server·DB): 정확한 호스트 중복, 새 snapshot전략/정렬, 당시 정책 조회·기록 상세 해석, 기존 데이터·세션 보존을 검증한다. 본 변경이 기존 승인/API-EXT-03, reconcile/API-EXEC-03, IMPORT 미확정 계약을 확정한 것은 아니다. actual Extension의1.2 대응·지원 버전 협상·설정은 통합 검토 필요, 실제 Chrome 적용은 미검증.

상세 도면 대응: ERD-04 sites(child-uq), ERD-05 site_feature_policies(parent0-uq)의 중첩 검사 문구를 정확한 호스트 중복으로 교체. ‘03-2 02 집중 중 · 정책 적용’의 정책 판단과 TF-A05(e)는 먼저 가장 구체적인 등록 호스트를 선택하는 것으로 갱신한다. 기존 정책 단계·나머지 노드/ID는 유지한다.
