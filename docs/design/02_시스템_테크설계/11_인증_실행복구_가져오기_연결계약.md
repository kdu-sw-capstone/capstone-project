# 인증·실행 복구·가져오기 연결 계약 — 2026-10-08

> 2026-10-09 D-01~D-10 사용자 확정 정책 반영: [최종 공용계약](FOCURVE_D01_D10_최종공용계약.md). 정책과 현재 제품 구현/검증을 구분한다. 아래 역사 JSON·현행 API는 보존하며 신규 복구 API가 구현된 것으로 해석하지 않는다.

사용자 요청으로 기존 담당 Web·Server·DB의 미구현 경로와 검토 F1–F7을 보완한다. 기존 기능 ID·담당 배정·필수/추가 구분은 유지한다. 이 문서는 아래 Server 구현의 구체적인 입출력 기준이다. Extension 담당자와의 합의·실제 Chrome 통합 완료를 의미하지 않는다. 원격 PR #17의 비회원 제품 코드에는 아래 회원 통신 어댑터가 없으므로 별도 연결 작업이 필요하다.

## 인증 (AUTH-01/02/03/05)

- Google: authorization code → Server token 교환 → Google JWKS로 RS256 ID token 서명, issuer, 만료, 발급 시각, audience, nonce 및 azp 검증. 공식 Google 사용자 식별자는 `sub`이다.
- 카카오: authorization code → Server token 교환 → 공식 `/v2/user/me`. 양의 정수 `id`를 사용자 식별자로 사용한다. 이메일은 `is_email_valid`와 `is_email_verified`가 모두 true인 경우만 인증된 연락처로 사용한다.
- 공통 식별키는 `(provider, subject)`이다. 같은 이메일을 가진 다른 회원을 자동 연결하지 않는다. 기존 이메일과 충돌하면 `409 IDENTITY_CONFLICT`, 기존 계정 로그인·재인증·명시적 연결로 안내한다.
- 로그인 callback이 기존 식별키를 찾으면 해당 회원으로 로그인한다. 신규 식별키는 가입 ticket을 만들고, 약관 동의·표시명·인증된 연락처가 준비된 후 가입 확정한다.
- OAuth state 5분, 가입 ticket 30분. state/ticket은 HttpOnly 브라우저 세션에 결속하고 단일 사용한다. 제공자 취소는 `#social-canceled`, 나머지 인증 실패는 안전한 오류 코드만 `#social-error`로 전달한다. 제공자 응답 본문·인증 코드·토큰을 로그에 남기지 않는다.
- 연결: 로그인한 현재 계정의 재인증 5분 이내에 `POST /auth/identities/link {ticket,consent:true}`. 다른 사용자의 제공자 계정/이미 연결된 식별키는 409. 제공자 인증 취소는 현재 회원 연결 상태를 변경하지 않는다.
- 카카오 등에서 인증 이메일이 없으면 가입 확정은 `422 CONTACT_EMAIL_REQUIRED`. `POST /auth/social/signup-info {ticket}` → `{provider,email,email_verified}`; `POST /auth/social/email-requests {ticket,email}` → 202; 메일 링크에서 `POST /auth/social/email/verify {token}` → `{verified:true}`. 원래 가입 창에서 상태를 갱신하고 가입 확정한다. 새 이메일 challenge는 20분·단일 사용이며 같은 가입 ticket의 이전 challenge를 대체한다. 이메일별 시간당 5회·최소 60초 간격, 발송 실패 시 challenge 저장은 롤백하되 요청 제한은 유지한다.
- 이메일 reset은 계정의 `auth_version`을 증가시키고 기존 Web 세션·Extension 토큰을 폐기한다. 비밀번호 검증 직후 reset이 완료되는 경쟁에서도 이전 인증 버전의 새 Web 세션 생성을 거절한다. 이메일 계정 자료는 삭제하지 않는다.
- 소셜 전용 계정은 FOCURVE 비밀번호를 새로 만들지 않는다. 공개 reset 요청 응답은 계정 존재 여부와 무관하게 동일한 202. 인증된 연락처에 제공자 계정 복구 안내를 보내며 RESET challenge는 발급하지 않는다.

## 외부 메일과 개발 메일

`MAIL_MODE=mailpit|external`; external은 `MAIL_TLS=true`(STARTTLS) 또는 `MAIL_SSL=true`(직접 TLS) 중 하나를 요구하며 서버 인증서를 검증한다. SMTP 연결/읽기/쓰기 제한 5초. 실제 수신 성공은 외부 메일함에서 별도 확인한다. SMTP가 접수한 사실만으로 실제 외부 배달 완료를 판정하지 않는다.

메일 링크 기준은 `AUTH_PUBLIC_URL`. 이메일 가입 인증 24시간, reset 30분, 소셜 연락처 인증 20분·단일 사용. 가입 발송 실패는 503+가입 롤백; 공개 재발송/reset의 202는 계정 조회 노출 방지용이며 발송 보장을 뜻하지 않는다. 실패한 challenge는 `delivery_status=FAILED` 기록, 재요청 제한은 유지한다. 메일함 링크는 Web `VITE_DEV_MAILBOX_URL`이며 기본 `http://127.0.0.1:8025`, 검토 환경 `http://127.0.0.1:8026`. 개발 빌드·mailpit 모드에서만 노출한다.

## 회원 연결 (EXT-01, AUTH-03)

기존 설치 proof·PKCE S256·state·등록 callback allowlist를 유지한다. 코드를 Web URL로 넘기는 방식 대신 설치의 인증된 polling으로 전달한다. Web은 code/proof/회원 bearer token을 보관하지 않는다. callback URI는 기존 설치 식별 allowlist 검증에 유지하며, 이 Server 버전의 전달 방식은 `EXTENSION_POLL`이다.

1. Extension은 비회원 활성 세션을 종료·자신이 소유한 규칙 해제를 확인한 뒤 journal에 `LINK_PENDING` 전환을 영속 저장한다. 승인/만료/거절 처리 전 새 비회원 실행을 시작하지 않는다.
2. 설치 proof 헤더 `X-Installation-Proof`로 `POST /extension-link-requests/{id}/evidence`. 모든 필드 필수:

```json
{"observation_id":"UUID","link_request_id":"UUID","owner_context":"GUEST:설치UUID","transition":"LINK_PENDING","active_session_id":null,"owned_rule_ids":[],"pending_action_count":0,"observed_at":"UTC ISO8601"}
```

관측은 과거 30초/미래 5초 이내. Server는 설치 인증과 보고·회원 활성 잠금을 검사한다. 이는 Chrome 실제 규칙의 독립적인 원격 증명이 아니다. 정직한 실제 조회·journal 순서는 Extension 담당 검증 대상이다.

3. Web의 기존 확인 화면에서 `POST /extension-link-requests/{id}/approval {approve:true|false}`. 증거 없거나 오래됐으면 409 `EXECUTION_EVIDENCE_REQUIRED`, 비회원 실행/잔여 규칙 보고는 `GUEST_SESSION_ACTIVE`; 타 계정 승인 변경은 거절. 승인 응답 `{approved:true,delivery:"EXTENSION_POLL"}`은 연결 완료가 아니다.
4. 설치 proof로 `POST /extension-link-requests/{id}/claim {state}`. 승인 전 `{status:"PENDING"}`; 승인 후 `{status:"APPROVED",code,state}`. 같은 요청의 응답 유실 재조회는 동일 code, 최초 claim부터 최대 60초. code는 DB에 hash만 저장한다.
5. 기존 `/extension-tokens`에서 code+verifier+proof를 교환한다. 단일 사용 및 설치/회원 활성 잠금을 다시 확인하고 토큰 발급. Extension은 회원 모드 전환을 journal에 저장하고 ACK 유실 복구를 처리해야 한다. code 교환 응답을 잃어 refresh token을 받지 못한 경우 임의 재발급하지 말고 연결 상태 확인·재연결 절차를 사용한다.

## 실행·복구·기록 (SESSION-01~04, EVENT-01~04, EXT-03)

접수 STARTING, 실제 APPLIED 보고 후 RUNNING, 실제 RELEASED 보고 후 종료라는 기존 불변 조건을 유지한다. APPLY 시작 시각은 명령 생성 시각보다 60초 넘게 과거일 수 없다. 이 60초는 클라이언트 시계 오차 허용이며 임의 과거 집중 시간을 인정하는 규칙이 아니다. 실행 기한 이후 APPLY는 해제 복구한다.

`POST /executors/{executor}/reconcile` (기존 API-EXEC-03, E 인증):

```json
{"journal_summary":{"format_version":"1.1","session_id":"UUID","known_revision":1,"last_report_id":null,"last_access_seq":0,"last_local_seq":0,"observed_at":"UTC ISO8601","observed_state":"RELEASED","final":true},"local_actions":[{"action_id":"UUID","local_action_seq":1,"session_id":"UUID","base_revision":1,"type":"END","observed_at":"UTC ISO8601","reason":"EXPIRED","report":{"report_id":"UUID","command_id":null,"session_id":"UUID","executor_id":"UUID","desired_revision":1,"result":"RELEASED","observed_at":"UTC ISO8601","intervals":[]}}]}
```

- 필수 MVP local action은 END. reason MANUAL/EXPIRED/BROWSER_RESTART/APPLY_FAILED. 실제 적용한 RUN은 시작·종료·duration_ms·CONFIRMED/UNCONFIRMED를 포함한다. 적용 없이 실패한 세션만 빈 intervals를 보낸다. PAUSE/RESUME는 추가 MVP이며 여기서 지원하는 것으로 표시하지 않는다.
- action seq는 세션별 1부터 연속, `(executor,action_id)`+payload hash 멱등성. revision은 이미 발급된 범위여야 한다. 다른 설치·세션 자료 변경 불가. action 결과와 interval·상태·잠금 해제를 한 transaction으로 저장한다.
- APPLY 보고 유실 후 offline 종료: 최초 APPLY 명령 기한/시계 범위와 일치하는 닫힌 RUN journal을 복구한다. summary가 APPLIED라는 이유만으로 RUNNING으로 바꾸지 않는다. 누락된 last_report 또는 STARTING에서의 APPLIED summary는 `REPORT_NOT_RECEIVED`; 저장된 원래 보고부터 다시 전송한다.
- 마지막 watermark는 해제 확인된 종료 세션에서만 저장한다. `last_local_seq`는 이벤트 envelope의 local_seq이고 local_action_seq와 별도다. 누락 이벤트가 있으면 PENDING, 정확한 seq/개수와 확정 interval이면 COMPLETE, 모순·미확인 interval이면 REVIEW_REQUIRED. 늦은 이벤트 수신 후 재계산한다.
- 중복 이벤트는 사용자 행을 먼저 잠가 receipt 부재 gap-lock 경쟁을 방지한다. 일시적 DB 충돌은 제한된 재시도 후 retryable503이며 영구 REJECTED로 ACK하지 않는다. 이벤트 local_seq 충돌은 409.
- target_key는 `SITE:canonical_host` 또는 `FEATURE:canonical_host:feature_code`. immutable snapshot에서 실제로 매칭된 정책과 event_type/reason이 일치해야 한다. 다른 target_key·미등록 차단·ALLOW 사이트의 차단 보고는 거절한다. 시간은 확정 RUN 안에서만 인정한다.

## 가져오기 (IMPORT-01/02)

기존 ImportItem의 필수 MVP type SITE/SESSION을 구현한다. CONTENT_POLICY/SCHEDULE·사용 시간 등 추가 MVP 자료는 `IMPORT_TYPE_UNSUPPORTED`로 분명히 거절하고 성공으로 숨기지 않는다. Extension 원본은 수정하거나 삭제하지 않는다.

- `POST /guest-imports` E + UUID Idempotency-Key, `{source_installation_id,manifest:[{type,source_item_id,source_hash}]}` → 202 ImportBatch. 1~100개 선택 목록; 빈 목록 불가. source_installation_id는 bearer 설치와 동일해야 한다.
- `PUT /guest-imports/{batch}/items/{source}` E, `{type,source_item_id,source_hash,payload}` → 항목 결과. Manifest에 없는 자료를 업로드할 수 없다. SITE payload는 기존 SiteWrite 필드이며, 원본의 url 값은 경로·query가 없는 정규화된 host여야 한다. 동일 canonical_host의 회원 설정(삭제된 이력 포함)은 `SKIPPED_CONFLICT`로 보존하며 자동 덮어쓰기/복원하지 않는다.
- source_hash = payload의 정규 JSON UTF-8 SHA256 소문자 hex. 객체 키는 사전순 정렬, 배열 순서 보존, 문자열 JSON escape·Unicode 정규화 없음. 숫자는 JS 안전 정수 범위만 허용, 실수 금지. 공통 fixture로 Extension과 byte 단위 대조해야 한다.
- 원본 귀속 `(source_executor_id,source_item_id)`는 최초 선택 계정에 영속 결속. 다른 계정 재이전 409, type/hash 변경 409. 동일 원본은 여러 batch에서 동일 결과를 조회하고 완료 항목을 다시 저장하지 않는다.
- item 단위 transaction, 실패 item은 FAILED+error_code, 다른 성공 item은 유지. batch PENDING/PARTIAL/COMPLETE. GET list를 기존 E에서 W/E로 확장해 Web 설정 화면에서 자기 처리 결과를 조회한다.
- SESSION payload: `{snapshot,session,events,intervals,usage_segments:[],note?,watermark?}`. session 필드 `session_id,executor_id,policy_snapshot_id,source,execution_status,duration_minutes,started_at,ended_at,policy_released_at,end_reason`. ENDED/START_FAILED이고 해제 시각=종료 시각, 종료 후 30일 이내만 허용. 추가 MVP 미수집 usage_segments는 빈 배열. 메모는 기존 구현 한도 2,000자.
- Snapshot은 기존1.1 또는1.2 구조, guest owner_user_id:null; 새 회원 snapshot UUID로 소유자를 바꾸고 events의 snapshot 참조를 같은 transaction에서 치환한다. 기록에는 origin=GUEST_IMPORT, 원본 source_session_id를 보존한다. active lock/실행 명령을 생성하지 않는다. interval 시간/중첩/기간 검증, 이벤트 기존 validator 재사용, 최대 집중 인정 시간은 목표 시간으로 제한, 나머지는 overrun.
- SessionBundle의 필수 필드를 잃거나 지원하지 않는 추가 기능을 조용히 버리지 않는다. item 실패 시 session·snapshot·event·note를 모두 롤백한다. 선택 manifest와 검증된 원본 payload는 DB에 보존한다.

## Web ↔ Extension 가져오기 어댑터 (구현된 Web 요청, 팀 합의·실제 연결 필요)

Web `VITE_EXTENSION_ID`에 고정 설치 ID를 설정한다. Chrome `runtime.sendMessage(extensionId,...)`를 사용한다. window.postMessage나 임의 origin의 토큰 전달을 사용하지 않는다. Extension manifest `externally_connectable.matches`는 승인된 Web origin만 허용하고 onMessageExternal에서 origin·현재 owner를 재검증한다.

- 사용자가 ‘가져올 자료 확인’ 클릭: `{type:"FOCURVE_GUEST_IMPORT_LIST",version:"1.0",owner_user_id}`. 응답 `{format_version:"1.0",owner_user_id,executor_id,items:[{type,source_item_id,source_hash,label}]}`. 본문/토큰 없이 목록만 반환. Web은 타 owner/잘못된 형식을 거절한다.
- 직접 선택 후 클릭: `{type:"FOCURVE_GUEST_IMPORT_SUBMIT",version:"1.0",owner_user_id,executor_id,request_id,items:[{type,source_item_id,source_hash}]}`. Extension이 사용자 선택과 원본 hash를 다시 확인하고 E 인증으로 Server에 manifest·payload를 전송, `{batch_id}` 응답. Web은 자기 계정 GET 결과로 저장 여부를 다시 확인한다.
- 로그인/화면 렌더만으로 목록 조회·업로드하지 않는다. 응답 유실 시 Server 처리 결과를 먼저 확인하고 미완료만 재선택한다. Extension이 원본을 자동 삭제하거나 보관 기한을 연장하지 않는다.
