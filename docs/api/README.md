# API 명세

## 목적

프로젝트에서 사용하는 API를 일관된 형식으로 관리하기 위한 문서입니다.

본 문서는 API를 사용하는 구성 요소가 동일한 기준으로 개발할 수 있도록 요청 방식, 응답 형식, 상태 코드 및 오류 처리 규칙 등을 기록하기 위해 사용합니다.

---

## 현재 상태

현재 프로젝트는 아이디어 기획 및 선정 단계입니다.

프로젝트의 기능과 기술 스택이 확정되지 않았으므로 실제 API 명세는 작성하지 않습니다.

현재 문서는 향후 API를 설계하고 기록하기 위한 기본 작성 규칙과 템플릿을 정의합니다.

---

## API 기본 정보

| 항목 | 내용 |
|------|------|
| Base URL | 미정 |
| API Version | 미정 |
| 통신 방식 | 미정 |
| Data Format | 미정 |
| Character Encoding | UTF-8 예정 |
| Authentication | 미정 |

프로젝트 주제와 기술 스택이 확정되면 실제 기준으로 수정합니다.

---

## 공통 요청 규칙

프로젝트 설계가 완료되면 다음 내용을 정의합니다.

- 요청 방식
- Request Header
- Content-Type
- 인증 및 권한 확인 방식
- 날짜 및 시간 형식
- Pagination 방식
- 정렬 및 검색 규칙
- 파일 업로드 방식
- 요청 데이터 검증 규칙

현재 단계에서는 특정 인증 방식이나 데이터 형식을 확정하지 않습니다.

---

## 공통 응답 형식

프로젝트에서 공통 응답 구조를 사용할 경우 모든 API에 일관되게 적용합니다.

아래 내용은 JSON 기반 API를 채택할 경우 사용할 수 있는 형식 예시이며, 실제 응답 구조는 프로젝트 설계 후 확정합니다.

### 성공 응답 예시

```json
{
  "success": true,
  "data": {},
  "message": "요청이 정상적으로 처리되었습니다."
}
```

### 실패 응답 예시

```json
{
  "success": false,
  "data": null,
  "message": "요청 처리 중 오류가 발생했습니다."
}
```

공통 응답 형식을 사용하지 않는 것으로 결정되면 실제 API 구조에 맞게 본 항목을 수정합니다.

---

## HTTP 상태 코드

HTTP 기반 API를 채택할 경우 다음 상태 코드를 기본 기준으로 검토합니다.

| 상태 코드 | 설명 |
|-----------|------|
| 200 | 요청 성공 |
| 201 | 리소스 생성 성공 |
| 204 | 요청 성공, 반환 데이터 없음 |
| 400 | 잘못된 요청 |
| 401 | 인증 필요 |
| 403 | 접근 권한 없음 |
| 404 | 리소스를 찾을 수 없음 |
| 409 | 데이터 충돌 |
| 500 | 서버 내부 오류 |

각 API에서 실제로 사용하는 상태 코드만 해당 API 명세에 작성합니다.

---

## API 분류

API는 프로젝트 주제와 핵심 기능이 확정된 후 기능 또는 도메인 단위로 분류합니다.

예시:

```text
[도메인명]
├── 데이터 등록
├── 데이터 조회
├── 데이터 수정
└── 데이터 삭제
```

현재 단계에서는 인증, 사용자, 통계 등 특정 기능이나 도메인을 미리 확정하지 않습니다.

## API 작성 양식

새로운 API를 명세할 때는 아래 형식을 사용합니다.

---

### API 이름

API의 목적과 처리 내용을 간단하게 작성합니다.

#### Endpoint

```http
GET /api/example
```

위 Endpoint는 작성 형식을 보여주기 위한 예시입니다.

---

#### Request Header

| 이름 | 타입 | 필수 | 설명 |
|------|------|------|------|
| 헤더 이름 | string | 선택 | 헤더의 용도 |

사용하지 않는 경우에는 `없음`으로 작성합니다.

---

#### Path Parameter

| 이름 | 타입 | 필수 | 설명 |
|------|------|------|------|
| id | string 또는 number | 필수 | 리소스 식별자 |

사용하지 않는 경우에는 `없음`으로 작성합니다.

---

#### Query Parameter

| 이름 | 타입 | 필수 | 설명 |
|------|------|------|------|
| page | number | 선택 | 페이지 번호 |
| size | number | 선택 | 페이지 크기 |

사용하지 않는 경우에는 `없음`으로 작성합니다.

---

#### Request Body

아래 내용은 JSON 형식을 사용하는 경우의 예시입니다.

```json
{
  "example": "value"
}
```

Request Body를 사용하지 않는 경우에는 `없음`으로 작성합니다.

---

#### Success Response

아래 내용은 공통 응답 형식을 사용하는 경우의 예시입니다.

```json
{
  "success": true,
  "data": {
    "id": 1
  },
  "message": "요청이 정상적으로 처리되었습니다."
}
```

---

#### Error Response

```json
{
  "success": false,
  "data": null,
  "message": "요청 처리 중 오류가 발생했습니다."
}
```

---

#### HTTP Status

| 상태 코드 | 발생 조건 |
|-----------|-----------|
| 200 | 요청이 정상적으로 처리된 경우 |
| 400 | 요청 데이터가 올바르지 않은 경우 |
| 404 | 요청한 리소스를 찾을 수 없는 경우 |

실제 API에서 발생할 수 있는 상태 코드와 조건만 작성합니다.

---

#### 비고

API 사용 시 필요한 추가 설명이나 주의 사항을 작성합니다.

예시:

- 인증 필요 여부
- 호출 제한
- 데이터 정렬 기준
- 중복 요청 처리 방식
- 관련 API 또는 문서

---

## 문서 관리 규칙

- API가 추가되거나 변경되면 관련 명세도 함께 수정합니다.
- 실제 구현 내용과 문서 내용이 일치하도록 유지합니다.
- 요청값과 응답값의 타입을 명확하게 작성합니다.
- 필수값과 선택값을 구분합니다.
- API 이름과 경로는 프로젝트 전체에서 일관된 기준을 사용합니다.
- 상태 코드는 발생 조건과 함께 작성합니다.
- 예시는 실제 구현에서 사용할 수 있는 형식으로 작성합니다.
- 확정되지 않은 기능이나 규격을 실제 적용 규칙처럼 작성하지 않습니다.
- 더 이상 사용하지 않는 API는 삭제 여부와 변경 이력을 팀원과 공유합니다.

## 향후 작성 예정

프로젝트 주제와 기술 스택이 확정되면 다음 내용을 추가하거나 구체화합니다.

- 실제 Base URL
- API 통신 방식
- API 버전 관리 정책
- 요청 및 응답 데이터 형식
- 인증 및 권한 관리 방식
- 공통 응답 형식
- 공통 오류 코드
- 예외 처리 규칙
- 날짜 및 시간 형식
- Pagination, 정렬 및 검색 규칙
- API별 상세 명세
- API 문서 자동화 도구 사용 여부
