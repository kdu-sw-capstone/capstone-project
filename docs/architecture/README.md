# 시스템 아키텍처

## 목적

본 문서는 프로젝트의 전체 시스템 구조와 구성 요소 간의 관계를 기록하고 관리하기 위한 문서입니다.

프로젝트에 참여하는 팀원이 시스템의 구성, 역할, 데이터 흐름 및 외부 연동 방식을 동일하게 이해할 수 있도록 기준을 제공합니다.

---

## 현재 상태

현재 프로젝트는 아이디어 기획 및 선정 단계입니다.

프로젝트 주제, 핵심 기능 및 기술 스택이 확정되지 않았으므로 실제 시스템 아키텍처는 작성하지 않습니다.

현재 문서는 향후 시스템 아키텍처를 설계하고 기록하기 위한 기본 작성 규칙과 템플릿을 정의합니다.

---

## 시스템 구성

프로젝트 주제와 기술 스택이 확정되면 실제 구성 요소를 작성합니다.

| 구성 요소 | 역할 | 사용 기술 | 상태 |
|-----------|------|-----------|------|
| 미정 | 미정 | 미정 | 검토 예정 |

구성 요소는 실제 프로젝트에 필요한 항목만 작성합니다.

프로젝트 확정 전에는 클라이언트, 서버, 데이터베이스, 확장 프로그램, 인공지능 서비스 등의 사용을 전제로 하지 않습니다.

---

## 시스템 구성도

프로젝트 설계가 완료되면 구성 요소와 연결 관계를 다이어그램으로 작성합니다.

작성 형식 예시:

```text
사용자 또는 외부 시스템
          │
          ▼
[입력 또는 인터페이스 영역]
          │
          ▼
[핵심 기능 처리 영역]
          │
          ▼
[데이터 저장소 또는 외부 서비스]
```

위 구조는 문서 작성 방식을 설명하기 위한 예시이며 실제 프로젝트 아키텍처가 아닙니다.

구성도에는 가능한 한 다음 내용을 표시합니다.

- 주요 구성 요소
- 구성 요소 간 연결 관계
- 요청 및 응답 방향
- 데이터 이동 방향
- 외부 시스템 연동 여부
- 배포 또는 실행 위치

---

## 구성 요소 작성 양식

각 구성 요소는 아래 형식으로 작성합니다.

### 구성 요소 이름

| 항목 | 내용 |
|------|------|
| 역할 | 구성 요소가 담당하는 기능 |
| 사용 기술 | 적용한 언어, 프레임워크 또는 도구 |
| 입력 | 전달받는 요청 또는 데이터 |
| 출력 | 반환하는 결과 또는 데이터 |
| 연관 요소 | 연결되는 다른 구성 요소 |
| 실행 환경 | 로컬, 서버, 브라우저 등 |
| 상태 | 예정, 설계 중, 개발 중, 완료 |

추가 설명이 필요한 경우 표 아래에 작성합니다.

---

## 데이터 흐름

프로젝트의 핵심 기능이 확정되면 기능별 데이터 흐름을 작성합니다.

작성 형식 예시:

```text
요청 발생
    ↓
입력 데이터 처리
    ↓
핵심 기능 수행
    ↓
데이터 조회 또는 저장
    ↓
결과 반환
```

실제 데이터 흐름을 작성할 때는 다음 내용을 포함합니다.

- 흐름이 시작되는 위치
- 전달되는 데이터
- 데이터를 처리하는 구성 요소
- 저장 또는 조회가 발생하는 위치
- 최종 결과가 전달되는 위치
- 오류가 발생할 수 있는 지점

기능마다 처리 과정이 다르면 데이터 흐름을 각각 작성합니다.

---

## 외부 시스템 및 서비스

외부 시스템이나 서비스를 사용하는 경우 아래 형식으로 기록합니다.

| 서비스 | 사용 목적 | 전달 데이터 | 인증 방식 | 비고 |
|--------|-----------|-------------|-----------|------|
| 미정 | 미정 | 미정 | 미정 | 미정 |

외부 서비스를 선정할 때는 다음 사항을 확인합니다.

- 프로젝트에 실제로 필요한가
- 무료 사용 범위와 비용은 적절한가
- 호출 제한이 있는가
- 개인정보 또는 민감한 데이터가 전달되는가
- 서비스 장애 시 대체 방법이 있는가
- 이용 약관과 라이선스에 문제가 없는가

현재 단계에서는 특정 외부 서비스를 사용한다고 가정하지 않습니다.

---

## 데이터 저장 구조

데이터 저장이 필요한 프로젝트로 확정되면 다음 내용을 작성합니다.

- 저장할 데이터의 종류
- 데이터 저장 방식
- 데이터 간 관계
- 데이터 생성 및 변경 주체
- 보관 기간
- 삭제 기준
- 백업 및 복구 방식

데이터베이스를 사용하는 경우 ERD를 별도로 작성하고 본 문서에서 연결합니다.

```text
ERD 문서 또는 이미지 링크: 추후 작성
```

## 보안 고려 사항

프로젝트 설계가 완료되면 실제 기능에 필요한 보안 기준을 작성합니다.

검토 항목은 다음과 같습니다.

- 사용자 인증 필요 여부
- 기능별 접근 권한
- 민감한 데이터 저장 여부
- 데이터 전송 보호 방식
- 비밀번호 및 인증 정보 관리
- 환경 변수 관리
- 개인정보 수집 및 보관 범위
- 외부 서비스로 전달되는 데이터
- 로그에 기록하면 안 되는 정보

사용하지 않는 보안 기술이나 인증 방식을 미리 확정하지 않습니다.

## 성능 및 안정성 고려 사항

프로젝트의 기능과 사용 환경이 확정되면 필요한 항목만 작성합니다.

검토 항목은 다음과 같습니다.

- 예상 사용자 또는 요청 규모
- 응답 속도 기준
- 반복 요청 처리 방식
- 대용량 데이터 처리 여부
- 캐시 필요 여부
- 비동기 처리 필요 여부
- 장애 발생 시 처리 방식
- 데이터 백업 및 복구
- 외부 서비스 장애 대응
- 로그 및 오류 추적 방식

프로젝트 규모에 필요하지 않은 복잡한 구조는 도입하지 않습니다.

## 배포 구조

배포가 필요한 프로젝트로 확정되면 다음 내용을 작성합니다.

| 항목 | 내용 |
|------|------|
| 배포 대상 | 미정 |
| 실행 환경 | 미정 |
| 배포 방식 | 미정 |
| 서버 또는 플랫폼 | 미정 |
| 도메인 | 미정 |
| HTTPS 적용 여부 | 미정 |
| 자동 배포 여부 | 미정 |

개발 환경, 테스트 환경 및 실제 배포 환경이 구분되는 경우 각각 작성합니다.

## 아키텍처 결정 기록

시스템 구조에 중요한 변경이 발생하면 결정 내용과 이유를 기록합니다.

| 날짜 | 결정 내용 | 선택 이유 | 검토한 대안 | 작성자 |
|------|-----------|-----------|-------------|--------|
| | | | | |

다음과 같은 결정은 기록 대상으로 봅니다.

- 주요 구성 요소 추가 또는 제거
- 기술 스택 변경
- 데이터 저장 방식 변경
- 외부 서비스 도입
- 인증 및 권한 구조 변경
- 배포 방식 변경

---

## 문서 관리 규칙

- 시스템 구조가 변경되면 본 문서도 함께 수정합니다.
- 실제 구현과 문서 내용이 일치하도록 유지합니다.
- 확정되지 않은 구성 요소를 실제 구조처럼 작성하지 않습니다.
- 아키텍처 다이어그램은 최신 상태로 유지합니다.
- 구성 요소의 역할과 연결 관계를 명확하게 작성합니다.
- 중요한 구조 변경은 변경 이유와 함께 기록합니다.
- 외부 자료나 이미지를 사용하는 경우 출처를 표시합니다.
- 민감한 정보는 문서에 작성하지 않습니다.
