# 팀 개발 가이드

본 문서는 캡스톤 프로젝트 팀의 개발 및 협업 방식을 정리한 문서입니다.

프로젝트를 진행하는 모든 팀원은 아래 절차와 규칙을 준수합니다.

---

## 개발 순서

프로젝트의 기본 개발 절차는 다음과 같습니다.

```text
develop 최신 Pull
        ↓
작업 브랜치 생성
        ↓
개발 또는 문서 수정
        ↓
Commit
        ↓
Push
        ↓
Pull Request 생성
        ↓
코드 리뷰
        ↓
Merge
```

---

## 작업 시작 전 확인 사항

작업을 시작하기 전에 다음 사항을 확인합니다.

- 최신 `develop` 브랜치를 Pull합니다.
- 작업 목적에 맞는 브랜치를 생성합니다.
- 작업 목적과 범위를 명확하게 확인합니다.

작업 종류에 따라 다음 브랜치를 사용합니다.

- 기능 개발: `feature/*`
- 버그 수정: `bugfix/*`
- 문서 수정: `docs/*`
- 리팩터링: `refactor/*`
- 환경 설정: `chore/*`

---

## 개발 중 준수 사항

- 하나의 브랜치에서는 하나의 목적에 해당하는 작업만 수행합니다.
- Commit은 의미 있는 작업 단위로 작성합니다.
- Commit 메시지는 `CONTRIBUTING.md`의 규칙을 따릅니다.
- 공용 설정 파일을 수정하는 경우 팀원에게 먼저 공유합니다.
- 담당하지 않은 주요 파일을 수정해야 하는 경우 담당자와 먼저 협의합니다.

---

## Pull Request 규칙

Pull Request를 생성하기 전에 다음 내용을 확인합니다.

- 작업 내용이 정상적으로 동작하는지 확인
- 불필요한 파일 제거
- Commit 메시지 확인
- 병합 대상 브랜치 확인 (`develop`)
- 비밀번호, API Key 등 민감한 정보 포함 여부 확인

---

## 절대 하면 안 되는 것

다음 행위는 원칙적으로 금지합니다.

- ❌ `main` 브랜치에 직접 Push
- ❌ `develop` 브랜치에 직접 Push
- ❌ 다른 팀원의 브랜치에서 작업
- ❌ 하나의 브랜치에서 서로 관련 없는 여러 작업 수행
- ❌ 작업 중인 변경사항을 정리하지 않고 다른 브랜치로 이동
- ❌ API Key, 비밀번호 등 민감한 정보 Commit

## 담당 영역

| 이름 | 역할 | 담당 영역 |
| --- | --- | --- |
| 김다훈 | Team Leader · 프로젝트 관리자 | Web / Server / Database / Integration |
| 윤종민 | Extension Core | 세션 상태, URL·Domain 감지, 사이트 차단·기록 정책, 차단 페이지, 시작·종료 연동 |
| 채지민 | Extension Content Control | Content Script, Shorts·내부 기능 제어, 행동 이벤트 생성·전송, Reels·추천·댓글·자동재생 확대 |

Popup·공유 모듈·Desktop 세부 작업은 관련 담당자와 이슈에서 배정합니다. 기존 책임을 임의로 다른 사람에게 넘기지 않습니다.

## 현재 GitHub 상태와 구현 시작 절차

2026-10-03 점검 기준 `main`과 `develop`은 PR 및 승인 1개를 요구하고 강제 Push·삭제를 제한합니다. 자동 테스트 워크플로와 필수 상태 검사는 아직 없습니다. PR 승인은 실행 검증 통과를 대신하지 않습니다.

1. 기능 이슈에 담당자, 관련 명세, 입력·기대 결과, 완료 기준을 적습니다.
2. `develop`에서 기능별 브랜치를 만듭니다. 변경 영역의 담당자가 리뷰합니다.
3. 실행 기반이 생기면 각 영역의 빌드·테스트를 CI에 추가하고, 통과한 검사를 필수 상태 검사로 연결합니다.
4. `develop` 통합 후 동일 버전의 테스트 증거를 남기고, 안정 버전은 PR로 `main`에 반영합니다.

현재 `frontend/`, `backend/`, `extension/`은 안내 문서 중심이며 실행 구현은 없습니다. `extension/core/`, `extension/content/`는 현재 경로가 아니라 향후 책임 분리를 위한 후보입니다.

---

## 문의 및 의사소통

- 기능 개발 전 담당자와 공유합니다.
- 공용 파일 수정 시 팀원에게 먼저 알립니다.
- Git 충돌(Conflict)이 발생하면 임의로 해결하지 말고 팀원과 함께 확인합니다.
- 작업 범위가 겹치는 경우 개발을 시작하기 전에 담당자를 조정합니다.
