## 3. A0 승인 후보 묶음 — 최종안에 선택을 고정할 것

### 범위와 버전

비회원·지원 https YouTube top-frame·**한 고정 활성 document/instance·선택행 한 정책**의 projection 제어시험. 최초 실제 제한 성공 시험은 media가 있는 Shorts viewer에서 수행한다. A0 시험 context는 격리된 fixture이며 실제 Guest 세션/회원 실행 권한으로 사용하지 않는다. navigation_id도 Core 시험 상관키일 뿐 접근 이벤트가 아니다.

버전 후보 `d06-shorts-a0-candidate-1`. 기존 rc1/draft4와 자동 fallback하지 않는다. 승인은 이 문서 최종 해시/SHA 및 최종 schema 문서에 묶어야 한다. 이름만 바꾸고 과거 JSON을 섞어 사용하지 않는다.

### 필드·QUERY 결속 후보

- envelope: 기존 request_id/type/owner_context/payload, 응답 request_id/status/data/error. strict allowlist, unknown/coercion 거절. QUERY null 예외 외 owner/context 필수.
- context: session_id/policy_snapshot_id/executor_id/desired_revision/document_id/navigation_id/binding_id. A0 한 binding만, Content는 발급하지 않는다. 원래 owner/frozen policy를 변환하지 않는다.
- QUERY 요청: contract_version/operation_id/operation/context/target_document_id. null 조회에는 owner_context=null/context=null만. 대상 echo는 인증 아님.
- null QUERY 응답 허용: contract_version/operation_id/operation/target_document_id/content_instance_id/adapter_ready. **binding_state/seq/operation/result/owner/session/policy를 반환하지 않는 최소안**으로 기존 draft4 응답보다 축소 제안. bound QUERY만 승인된 scope의 현재 상태·결과 제공.
- APPLY/RELEASE 요청에 QUERY로 확인한 content_instance_id 필수 후보. Core는 실제 document 지정 routing·registry epoch·지원URL/frame0를 대조. Content는 실제 같은 확장 Core 발신 context를 확인하고 body의 ID만 믿지 않는다.
- Core→Content sender에 tab/documentId가 항상 있다고 가정하지 않는다. Chrome의 실제 필드 확인 후 worker 식별 규칙을 승인한다. 공식 MessageSender의 관련 필드는 optional이다. 안전하게 식별할 수 없으면 구현 방식 재조율, popup 예외 허용으로 우회하지 않는다.
- APPLY: 기존 control_seq/context/observation round/policy/rule_id 및 instance. RELEASE: 원래 applied_binding_id와 종료 권한/context, policy/새관찰round 없음. instance 일치 확인. 최초 성공/실패 결과 불변, 현재 QUERY 별도.
- owner 전환·재binding·다중문서는 A0 비활성. 기존 owner cleanup 의무를 새owner가 임의 해제할 권한으로 삼지 않는다.

### 순서·상한·해제 보장 후보

정규 명령은 document 수명 동안 양의 safe integer seq 증가. 같은 ID/동일 의미는 in-flight 공유 또는 최초 data 반환, 다른 의미는 OPERATION_CONFLICT. cache eviction된 seq≤high-water는 STALE_CONTROL이며 재실행0. ID 지문은 승인된 A0 수명 동안 보존하고 예산 부족이면 새 APPLY 거절. 무한 bounded cache만으로 과거 모든 ID 재사용 탐지가 가능하다고 주장하지 않는다.

seqMAX 해제는 **미해결 blocker**다. 권장 비교안:

1. 정규 seqMAX를 유지하면서 별도 **cleanup-only 권한 경로**를 승인. 원래 binding·owner·document/instance·epoch를 검증한 RELEASE만 허용하고 신규 정책 적용 권한 없음. 진입 즉시 기존 APPLY epoch 폐기·그 instance 신규 APPLY 금지. 실패 ledger 보존/새 cleanup operation으로 재시도. 이 경로의 정확한 필드/ID중복·저장 실패 규칙을 Core와 별도 schema로 승인해야 하며 현재 구현됐다고 보지 않는다.
2. A0에서 APPLY 허용 횟수/seq를 사전 제한하고 cleanup seq 여유를 예약. 일반적인 포화시험에는 유용하지만 유한 여유 소진 뒤 RELEASE까지 보장하는 해법이 아니므로 **seqMAX 보장 기준 통과 대안은 아님**. 이를 택하면 미검증·별도 차단점으로 세 명이 명시해야 한다.

Content 직렬 queue만으로 RELEASE가 지연되는 것을 막기 위해 검증된 RELEASE 수신 시 옛 async 관찰 epoch를 중단하는 후보. DOM mutation 실행은 직렬화하고 동일명령 replay가 재중단/재적용을 일으키지 않게 검증한다. 취소된 옛 APPLY 성공은 현재 결과로 수용하지 않는다. 완료 cache 교체는 ledger/원래 binding/정책식별/cleanup 의무를 제거하지 않는다.

### 실제 적용·복원 기준 후보

| 상태 | 필요한 실제 증거 | 성공 의미 |
|---|---|---|

## 4. A0 필수 결정과 비활성 범위

| A0 착수 전 반드시 명시 승인 | A0 비활성/후속, 기준 통과로 올리지 않음 |

A1은 실제 Guest frozen Snapshot 생성·전체 검증·선택행 전달·제품 시작/해제 집계다. A0 fixture 성공을 A1 성공, RUNNING 시작 허가, D07 gate 해제, D06-T01~28 전체 성공으로 쓰지 않는다. A0라도 기존 SITE/Event pipeline에 fixture를 넣어 실제 기록을 만드는 부작용이 없어야 한다.

## 5. 담당 변경 경계와 시험 순서

- Core(종민): 승인 후 manifest/주입·문서 결속·발신 adapter, registry seq/command·결과 집계·cleanup-only 선택 구현. 기존 Guest 활성true 거절을 A0 fixture 때문에 무조건 제거하지 않음.
- Content(지민): 승인 후 singleton bootstrap/수신 adapter·strict validator·직렬 queue/취소epoch·불변응답, shorts 실제 census와 changes 복원 검증. 신규 파일명은 양측 경로 충돌 확인 후 정하고 지금 만들지 않음.
- 다훈: A0 최종 schema/수용표·G-01 예외를 취합. Server runtime/Event 영향은 후속 미합의로 보존하고 SV 검증 근거를 제품 연결 완료와 분리.

시험 1: schema/원문 충돌·stale scope·wrong instance·동일ID/높은seq·eviction·cache/queue 포화·seqMAX RELEASE·저장실패·해제 실패 후 새명령·옛 async 재가림0. **모의 검증**.

시험 2: Chrome 합성 DOM의 미지원/무대상/media0/다중viewer/재생실패/복원silent실패/사용자후속스타일보존. **합성 검증**.

시험 3: 실제 Windows MV3 worker sender·주입 singleton·document routing→실제 제품 YouTube Shorts 숨김/무음·적용결과→해제·직접재생 가능. URL변화/pagehide/응답유실은 정상완료 제외·남은 의무 기록. **실제 제품 검증**.

각 시험은 승인 schema SHA·Core/Content SHA·Chrome/OS·명령·원문 status와 증거·실행 주체를 남긴다. A0 한 항목 실패/미확인은 정상완료 금지. 실패 수정 후 관련 회귀, 기존 추가 MVP는 보존.
